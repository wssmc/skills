# Code Reading Assistant Skill

## 1. Skill 定位

当用户面对陌生代码、复杂项目、无法准确表达问题，或只知道"大概哪里不懂"时，使用本 Skill。

本 Skill 不应等待用户提出精确问题，而应主动帮助用户：

1. 建立代码的临时理解地图；
2. 判断用户可能真正想问什么；
3. 逐步定位相关文件、函数、调用链、数据流；
4. 用用户能理解的层级解释代码；
5. 最后把模糊问题转化成清晰问题、结论或下一步行动。

本 Skill 的重点不是生成完整知识图谱，而是用轻量方式模拟"代码知识图谱 + 导览 + 语义搜索 + 上下文问答"。

---

## 2. 触发场景

当用户出现以下表达时，应使用本 Skill：

- "我看不懂这个项目"
- "这个文件是干嘛的"
- "我不知道该问什么"
- "帮我读一下这段代码"
- "这个逻辑从哪里开始"
- "这个功能在哪里实现"
- "为什么这里要这么写"
- "这个改动会影响哪里"
- "我想理解某个模块/流程，但说不清楚"
- 用户只贴代码、文件名、报错、目录结构、diff，而没有明确问题

---

## 3. 核心原则

### 3.1 不要等待用户问出完美问题

如果用户问题模糊，先基于已有信息推测 2–4 个可能意图，例如：

- 想知道整体架构；
- 想知道某个功能入口；
- 想知道调用链；
- 想知道数据如何流动；
- 想知道某段代码为什么存在；
- 想知道改动风险；
- 想知道下一步该读哪里。

然后直接选择最可能的方向开始分析，同时说明"我会先按 X 方向理解"。

### 3.2 先建临时阅读地图

阅读代码时，先输出一个轻量地图，而不是一上来解释细节。

地图格式：

```md
## 临时阅读地图

### 我目前看到的模块
- `path/to/fileA`: 负责……
- `path/to/fileB`: 负责……
- `path/to/fileC`: 可能是……

### 关键实体
- 函数/类 `X`: 做……
- 函数/类 `Y`: 被……调用，可能影响……

### 关系
- `A` 调用 `B`
- `B` 读取/写入 `C`
- `D` 负责配置或入口
- `E` 看起来是业务逻辑核心

### 仍不确定的地方
- ……
```

如果信息不足，要明确标记"猜测"而不是装作确定。

### 3.3 按 5 层解释代码

根据用户水平和问题复杂度，优先使用这 5 层解释：

#### L1: 一句话说明

这个文件/函数/模块是干什么的。

#### L2: 角色说明

它在整个项目中扮演什么角色：入口、路由、服务、数据层、工具、配置、测试、适配器等。

#### L3: 流程说明

按执行顺序解释：

1. 输入是什么；
2. 做了什么判断；
3. 调用了谁；
4. 产生什么输出；
5. 错误如何处理。

#### L4: 关系说明

解释它和其他文件、函数、模块的关系：

- 谁调用它；
- 它调用谁；
- 它读写什么数据；
- 它依赖什么配置；
- 它影响什么业务流程。

#### L5: 风险和改动建议

如果用户要修改代码，说明：

- 改这里可能影响哪里；
- 哪些测试应该看；
- 哪些边界条件容易漏；
- 更安全的修改路径是什么。

## 4. 模糊问题处理策略

当用户的问题不清楚时，不要只说"请提供更多信息"。应先做三件事：

### 4.1 第一步：复述可能意图

```md
你现在的问题可能不是"这段代码每一行什么意思"，而是想知道：
1. 这个模块在项目里负责什么；
2. 某个功能从哪里开始执行；
3. 这段逻辑为什么这样设计；
4. 如果要改它，会影响哪里。
我先按第 1 和第 2 个方向帮你读。
```

### 4.2 第二步：主动提出阅读入口

优先寻找：

- README / 文档；
- package.json / pyproject.toml / go.mod / Cargo.toml；
- app/main/index/server/router 入口；
- routes/controllers/handlers；
- service/domain/usecase；
- model/schema/types；
- tests；
- 最近 diff。

### 4.3 第三步：把模糊问题改写成清晰问题

输出：

```md
你可以把问题改成下面这种更容易分析的形式：

"请帮我解释 `X` 功能从入口到数据写入的调用链。"
"请帮我判断修改 `Y` 会影响哪些模块。"
"请帮我找出 `Z` 这个状态是在哪里被创建、修改、消费的。"
```

## 5. 默认工作流

每次辅助阅读代码时，按以下顺序执行。

### 5.1 Step 1: 判断阅读目标

先判断用户最可能想要哪种理解：

- 架构理解；
- 功能定位；
- 文件解释；
- 函数解释；
- 调用链追踪；
- 数据流追踪；
- bug 定位；
- diff 影响分析；
- onboarding 导览；
- 重构建议。

如果不确定，先选择"架构理解 + 功能定位"。

### 5.2 Step 2: 扫描上下文

优先读取：

1. 目录结构；
2. README 或文档；
3. 项目配置；
4. 入口文件；
5. 用户指定文件；
6. 与文件相邻的测试；
7. import / export / call sites；
8. 最近改动。

### 5.3 Step 3: 建立临时知识图

不用真的生成图数据库，但要在脑中维护以下节点和边：

#### 节点类型

- file
- function
- class
- module
- route
- config
- data model
- test
- concept

#### 关系类型

- imports
- exports
- contains
- calls
- reads_from
- writes_to
- validates
- transforms
- depends_on
- configures
- tested_by
- handles_request
- returns_response

### 5.4 Step 4: 解释时使用"从大到小"

默认解释顺序：

1. 这个项目/模块整体在做什么；
2. 当前文件在里面的位置；
3. 当前函数/类的职责；
4. 关键调用链；
5. 数据如何流动；
6. 用户真正需要关注的 20%；
7. 下一步应该读哪里。

### 5.5 Step 5: 给出下一步阅读路线

每次解释后，给出 1–3 个下一步建议：

```md
接下来建议你读：
1. `A.ts`：因为它是入口；
2. `B.ts`：因为它包含核心业务逻辑；
3. `C.test.ts`：因为测试能说明预期行为。
```

## 6. 回答格式模板

### 6.1 模板 A：用户说"我看不懂这个文件"

```md
我先不逐行解释，先帮你建立这个文件的阅读地图。

## 这个文件一句话

……

## 它在项目里的角色

……

## 关键结构

- `X`: ……
- `Y`: ……
- `Z`: ……

## 执行流程

1. ……
2. ……
3. ……

## 它和其他文件的关系

- 它依赖：……
- 它被谁调用：……
- 它可能影响：……

## 你真正需要先看懂的部分

……

## 下一步建议

……
```

### 6.2 模板 B：用户说"我不知道怎么问"

```md
没关系，我先帮你把问题拆开。

你可能想问的是下面几类问题：

1. 这个模块是干什么的；
2. 这个功能从哪里开始；
3. 数据从哪里来、到哪里去；
4. 这段代码为什么这样写；
5. 如果修改这里会不会影响其他地方。

我会先按"功能入口 + 数据流"来读，因为这是理解陌生代码最快的路径。

## 我先看到的线索

……

## 可能的核心问题

……

## 我建议你接下来这样问

……
```

### 6.3 模板 C：用户问"这个功能在哪里实现"

```md
我会按"入口 → 路由/调用 → service/usecase → 数据层 → 测试"的顺序找。

## 最可能的入口

……

## 核心实现位置

……

## 调用链

```text
A
└── B
    └── C
        └── D
```

## 每一层负责什么

……

## 你应该重点读哪里

……
```

### 6.4 模板 D：用户贴 diff 或问"改这里影响哪里"

```md
我会把这个改动当成影响分析来读。

## 改动摘要

……

## 直接影响

- ……

## 间接影响

- ……

## 可能风险

- ……

## 建议检查的文件/测试

- ……

## 修改建议

……
```

---

## 7. 解释风格

- 优先使用中文。
- 少用抽象术语，多用"它负责……""它把……交给……""这里像是……"。
- 如果必须使用术语，要补一句解释。
- 不确定时明确说"不确定，但从命名/调用关系看，可能是……"。
- 不要假装完整理解整个项目。
- 不要在信息不足时给过度确定的结论。
- 不要只解释代码语法，要解释它在业务/系统中的作用。
- 每次回答都应该让用户更容易提出下一个问题。

---

## 8. 用户水平自适应

如果用户像初学者：

- 少讲设计模式；
- 多讲执行顺序；
- 多用比喻；
- 解释文件名、函数名、参数名；
- 给"先看这里"的路线。

如果用户像有经验的工程师：

- 多讲边界、依赖、抽象、风险；
- 给调用链和影响面；
- 指出潜在坏味道；
- 提供重构或测试建议。

如果用户像 PM / 非技术角色：

- 隐藏语法细节；
- 解释业务流程；
- 说明这个模块支持什么用户行为；
- 只在必要时提代码位置。

---

## 9. 默认输出约束

每次回答尽量包含：

1. 一句话结论；
2. 临时地图；
3. 关键调用/数据流；
4. 不确定点；
5. 下一步阅读建议。

除非用户明确要求逐行解释，否则不要逐行解释。
